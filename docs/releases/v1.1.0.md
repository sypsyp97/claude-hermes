## Conversation and attachment improvements

- Telegram and Discord carry bounded reply/forward context with source labels. Telegram forwarded commands and transcriptions remain quoted data. Discord can fetch missing same-channel reply content before checking whether it replies to the bot.
- Discord downloads multiple images and generic files, with current attachments ahead of referenced ones and original filename/path mappings. Telegram accepts generic documents, including missing MIME types, and exposes media from replied-to messages.
- Both bridges deliver generated artifacts through explicit `[send-file:...]` directives. Discord supports ordinary messages and skill slash commands. Each conversation has its own validated outbox; files outside it, escaping symlinks and aliased roots are rejected.
- Downloads are bounded to 20 MiB per file; Discord admits at most ten input files per message. Each output is capped at 10 MiB. Telegram album updates remain individual ordered turns; archives are not automatically extracted.

## Session controls and channel policies

- `/cancel`, `/kill` and `/stop` signal only the current conversation's active Claude task, including a task waiting for a process slot. Commands bypass the occupied message lane; mentions and Telegram captions use the same parsing rules. Ordinary prose remains a message. Other conversations and future queued messages are retained.
- `/model [default|sonnet|opus|haiku|model-id]` persists a per-conversation model preference in SQLite. `/status` reports the same preference. `/model default` restores inherited routing.
- `/verbose [on|off]` persists detailed progress preferences. Telegram and Discord show bounded answer previews, with coalesced edits and a completion summary before the full final answer. Closing or cancelling a task finishes its status lifecycle.
- Discord guild-channel policies accept additional `allowedUserIds`; threads inherit the parent policy unless overridden. Grants apply to messages and interactions within that channel, and never grant DM access. Thread management requires global authorization.

## Automation and maintenance

- Job files support `notifyChannel`, `notifyTelegramChat` and `notifyTelegramTopic`. Explicit targets replace default forwarding for that job, including its progress destination. Failed or disabled targets never redirect results to other recipients. Invalid targets reject the job at load time. `notify: false` and `notify: error` suppress live progress.
- Skill search uses the structured skills.sh API with timeout, response validation and HTTP error reporting.
- `/context` normalizes Claude project slugs and locates moved transcripts by exact session UUID.
- Discord system messages are filtered before model invocation. Transport retries continue to distinguish explicit rate-limit rejections from uncertain writes.

## Upgrade notes

Claude Code **2.1.257+** remains required. No runtime dependency or SQLite schema migration was added. New model/verbosity settings use the existing policy store.

Existing Telegram skills that emit arbitrary local file paths must write or copy outputs into the per-conversation outbox supplied in the Claude system prompt. Cancellation does not undo completed side effects or cancel attachment preparation. Shared workspaces remain trusted environments rather than operating-system sandboxes.

English and Chinese READMEs describe commands, limits, authorization, and notification settings. Validation uses fake Claude and mocked platform APIs, with regression tests added before fixes and independent fresh-context review after implementation rounds. Actual bot credentials and paid Claude requests are not used by the automated suite. Publication requires the Ubuntu/macOS × Bun 1.3.4/latest verification matrix.
